# LotTrace Manual Test Data Bible

> Working branch: `audit-fixes` (HEAD `38ba59f`).
> Source of truth: application code, migrations, and Zod schemas.
> Documentation is compared against code, never used as the source of truth.

---

## 1. What this pack is

This directory is a complete, reproducible manual-testing data set for LotTrace. It covers:

- every database entity and its fields, including system and hidden fields;
- every screen, form control, filter, modal, and settings page present in the code;
- every API endpoint, payload shape, status code, and role gate;
- every business rule that a tester can exercise, positive and negative;
- CSV import fixtures with exact expected success and error output;
- end-to-end scenarios that chain records across entities and roles.

Every rule is cited as `path/to/file:line`. Where a fact could not be established from code or documentation, it is marked `[UNVERIFIED]`, with the reason.

---

## 2. How to use the pack

1. Reset the disposable development database and run migrations and seeds.
2. Create the organizations and users from `10_organizations.md` and `11_users_auth.md`.
3. Create locations, products, lots, and events in ID order. Later records reference earlier ones.
4. Run the import fixtures in `imports/` with the expectations in `40_import_files.md`.
5. Execute the scenarios in `30_scenarios_e2e.md` with the role matrix in `20_auth_roles.md`.
6. Record actual results. Report any mismatch between expected and actual in `99_discrepancies_and_findings.md`.

Do not copy values across organizations. Tenant isolation tests depend on identical-looking names existing in different organizations.

## 4. Data conventions

### 4.1 Identifiers

Business IDs in this pack are stable test labels, not database UUIDs:

| Prefix | Entity | Example |
|---|---|---|
| `ORG-` | Organization | `ORG-001` |
| `USR-` | User | `USR-004` |
| `LOC-` | Location | `LOC-003` |
| `PRD-` | Product | `PRD-012` |
| `LOT-` | Lot | `LOT-020` |
| `EVT-` | Event | `EVT-011` |
| `ATT-` | Attachment | `ATT-002` |
| `IMP-` | Import job | `IMP-004` |
| `REC-` | Recall simulation | `REC-003` |
| `EXP-` | Report export | `EXP-005` |
| `NTF-` | Notification | `NTF-006` |
| `NEG-` | Negative case | `NEG-EVT-03` |

When entering data in the UI, use the UUIDv4 generated by the application. The pack's business ID is for traceability in test notes only. The exception is user-supplied codes such as `traceabilityLotCode`, SKU, GLN, and import `transaction_id`, which are entered verbatim.

### 4.2 Fake data

All generated organizations, people, addresses, phone numbers, tax IDs, and domains are fictional:

- Emails use `example.com`, `example.org`, or subdomains of those.
- Phone numbers use the North American `555-01xx` range.
- Tax IDs use `00-0000000` style placeholders.
- No real company, person, or address is represented.

The one fixed non-example address is the seeded platform account `admin@lottrace.com`. It is hard-coded in `backend/src/db/seed-super-admin.js:7` and is a system account, not generated test data.

### 4.3 Passwords

All generated active users use:

```text
LotTrace!Test2026
```

This is 16 characters and satisfies the only code-enforced rule: minimum 8 characters (`backend/src/modules/auth/auth.validation.js:7`). There is no uppercase, number, or symbol requirement in code. The pack uses a strong password anyway so the data is safe to reuse.

The seeded super admin password is whatever the operator sets in `SEED_SUPER_ADMIN_PASSWORD`. The seed requires at least 12 characters (`backend/src/db/seed-super-admin.js:8,132-135`). Example only:

```text
SuperAdmin!Test2026
```

### 4.4 Dates

- Event times are ISO-8601 UTC strings with milliseconds, e.g. `2026-06-15T08:00:00.000Z`.
- The web form submits `datetime-local` values converted to ISO UTC (`frontend/src/pages/events/recordEventPayload.js:22`).
- The imported `event_datetime` column accepts any string that JavaScript `new Date()` can parse (`backend/src/jobs/workers/import-processor.js:52-59`), even though the UI label says ISO.
- Relative dates are anchored to **2026-06-01 through 2026-06-30** so scenarios stay reproducible.

### 4.5 Organization, user, and role scope

- Five active organizations carry data.
- A sixth organization is deliberately empty for empty-state and onboarding tests.
- Each active organization has at least one `org_admin`, one `compliance_manager`, two `operator`s, and one `auditor`, except where a scenario explicitly tests a missing role.
- `super_admin` exists only through the seed script. There is no UI or API to create one.

## 6. Response and error conventions used in expectations

Success responses always use one of these envelopes (`backend/src/utils/apiResponse.js:10-32`):

```json
{ "success": true, "message": "Success", "data": {} }
```

```json
{ "success": true, "message": "Fetched successfully", "data": [], "pagination": {} }
```

Error responses always use (`backend/src/utils/apiResponse.js:38-41`, `backend/src/middleware/errorHandler.js:56-77`):

```json
{
  "success": false,
  "message": "Validation failed",
  "error": {
    "code": "VALIDATION_ERROR",
    "details": [{ "field": "email", "message": "Invalid email address" }]
  }
}
```

Standard pagination metadata is `total`, `page`, `limit`, `totalPages`, `hasNextPage`, `hasPrevPage` (`backend/src/utils/pagination.js:17-28`). The event list is the exception: it uses keyset pagination with `limit`, `hasNextPage`, `nextCursor` (`backend/src/modules/events/events.service.js:207-270`).

When this pack says "expect 422", read the exact message and field from the relevant entity file. Zod errors surface the first failing rule per field; nested arrays use dotted paths such as `inputs.0.quantity` (`backend/src/middleware/errorHandler.js:56-66`).

## 7. Reset procedure between runs

```bash
cd backend
npx knex migrate:rollback --all
npx knex migrate:latest
npx knex seed:run
```

After reset, repeat `10_organizations.md` and `11_users_auth.md`. Do not reuse an old JWT: access tokens last 30 minutes and refresh tokens last 7 days (`backend/src/modules/auth/auth.service.js:62-72`), and deactivation writes a Redis deny key (`backend/src/middleware/authenticate.js:48-71`).

To clear only cache and rate limits:

```bash
redis-cli FLUSHDB
```

This also deletes pending signups (`signup:<email>`) and password-reset state. That is intended in a disposable environment.

## 8. Quality gates applied to this pack

- **Coverage:** every backend module mounted in `backend/src/app.js` has a matching file; every table in `backend/src/db/migrations/` appears in `02_field_registry.md`.
- **Consistency:** organization, user, location, product, lot, and event IDs are unique and referenced consistently across files.
- **Constraint spot-checks:** at least 20 constraints were re-read from code and cited at the exact line; see `90_coverage_matrix.md` §5.
- **Honesty:** items that cannot be verified without running the app are marked `[UNVERIFIED-RUNTIME]`; items contradicted by code are in `99_discrepancies_and_findings.md`.
- **No source changes:** this pack adds files only under `docs/test-data/`.

## 9. Known limits

- Expected messages are code-derived. Actual browser toasts may replace some server messages with generic text. Scenario files state both where they differ.
- File upload, email delivery, BullMQ timing, and S3 presigned URLs require running infrastructure. Those steps are marked `[INFRA]`.
- `super_admin` behavior is documented from middleware code, not from a complete admin UI. No super-admin screens exist in `frontend/src/App.jsx`.
- One event-list behavior (`lot_links` ordering) is not guaranteed by SQL and is marked `[UNVERIFIED-RUNTIME]` where order matters.
